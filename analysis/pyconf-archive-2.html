Two Test Tiers

How Students Answer

Question 1: Card to Value Tuple

Parsing by Shape, Not Contract

card_to_value_tuple('AH') → (2, 1)   # suit H=2, rank A=1
card_to_value_tuple('7D') → (3, 7)   # suit D=3, rank 7=7
Private tests include: 10H → (2, 10)  ·  AC → (4, 1)

Suits: S=1, H=2, D=3, C=4    Ranks: A=1, 2–10=number, J=11, Q=12, K=13

This question has one beautiful trap. The public examples are all 2-character cards. But 10D is 3 characters.

Student 1 — The Baseline

suit = card[-1]
rank = card[:-1]

suit_val = suit_values[suit]
if rank in rank_values:
    rank_val = rank_values[rank]
else:
    rank_val = int(rank)

return (suit_val, rank_val)
Public 2/2 ✓ Private 2/2 ✓

t = 6 seconds · No edits

This student modelled the input as a variable-width string before touching the keyboard. card[-1] is always the suit. card[:-1] is always the rank.

Ten seconds, full marks. This is what it looks like when someone reads the contract before they read the examples.

Student 2 — The Productive Struggle

rank, suit = card        # unpacking a string

if rank in rank_values:
    r = rank_values[rank]
else:
    r = rank
if suit in suit_values:
    s = suit_values[suit]
else:
    s = suit

return tuple(s, r)       # ← TypeError!
Public 0/2 ✗ t = 193s

TypeError: tuple expected at most 1 argument, got 2

Everything is right except the punctuation.

The student had the right idea — get both values and return them. But tuple(a, b) isn't how you make a tuple from two values. Everyone has done this.

Student 2 — One Fix, One Remaining Bug

rank, suit = card

if rank in rank_values:
    r = rank_values[rank]
else:
    r = rank
if suit in suit_values:
    s = suit_values[suit]
else:
    s = suit

return (s, int(r))      # ← fixed!
Public 2/2 ✓ t = 246s

53 seconds to fix the tuple bug and pass public tests

⚠ But what happens when card = '10H'?

The Hidden Boss

10D

'AH' → rank='A', suit='H' ✓

'7D' → rank='7', suit='D' ✓

'10H' → ValueError: too many values 💥

Private 1/2 ✗ — score 50

The only two-digit rank in the deck walks on stage like a hidden boss, and rank, suit = card dies in one step.

This is the conceptual anchor for the whole talk: the visible examples are not the task.

Student 3 — Parsing by Index

i = 2
while i <= 10:
    rank_values[str(i)] = i
    i += 1

result = (suit_values[card[1]],
          rank_values[card[0]])
return result
card[0] = rank  ·  card[1] = suit
Public 2/2 ✓ Private 1/2 ✗

711 seconds of work

For '10D': card[0]='1', card[1]='0'
KeyError — neither is in rank_values

This student built up the rank_values dict with a while loop — clever! But card[0]/card[1] indexing assumes the card is always exactly 2 characters.

The Visible Examples Are Not The Task.

Public tests show AH and 7D.
Neither has a two-digit rank. The hidden test needed just one.

That gap between public and private tests — let's see it again, on a harder question.

Question 2: Check for Greeting Prefix

Negotiating With the Tests

starts_with_greeting('Hello world') → True
starts_with_greeting('Hi there') → True
starts_with_greeting('Goodbye') → False
starts_with_greeting('Hithere') → False  # no space after Hi

Must start with 'Hello ' or 'Hi ' — trailing space matters.

This question has three different failure modes on the same tiny problem. Maximum contrast from minimum code.

Student 1 — The Baseline

return s.startswith('Hello ') or s.startswith('Hi ')
Public 4/4 ✓ Private 3/3 ✓ 1 second

The student read the sentence "starts with Hello or Hi followed by a space" and wrote exactly that in Python. Nothing more.

Student 2 — A JavaScript Accent

if s.startswith('Hello'|| 'Hi'):
    return True
return False
SyntaxError t = 0s

Python, but spoken with a JavaScript accent. The intent is perfect. The operator is from another universe.

Read it out loud. Let the audience catch it first. The double-pipe is the JavaScript OR operator.

Student 2 — Closer, But...

if s.startswith('Hello' or 'Hi'):
    return True
return False
Public 3/4 t = 24s

'Hello' or 'Hi' evaluates to 'Hello' — truthy wins.
So this is just startswith('Hello'). The 'Hi' cases all fail.

What this tells you: surface intent can be completely correct while language fluency is still catching up.

Negotiating With the Grader

if s == 'Hithere':
    return False
if s.startswith('Hello' or 'Hi' or 'hello' or 'hi'):
    return True
elif s.startswith('Hi'):
    return True
return False
Public 3/4 t = 4238s

The student has entered treaty negotiations with the grader. One visible test case, one explicit patch. This is not debugging — this is diplomacy.

The audience has definitely seen this behavior in a pull request at some point. An if-statement for every known failing input.

Student 3 — The Triple-Quoted Graveyard

'''if s[0] == "Hello":
    return True
if s[0] == "Hi":
    return True
else:
    return False'''
if not isinstance(s, str):
    return False
return s.startswith('Hello') or s.startswith('Hi')
Public 3/4 t = 629s

Old (wrong) code triple-quoted. New code runs. But missing trailing space — still 3/4.

Students use triple-quote comments as ad-hoc version control. This is version control by burial.

The Graveyard Flip

t = 4826s — correct-ish code restored, running:

if not isinstance(s, str):
    return False
s = s.strip()
return s.startswith('Hello') or s.startswith('Hi')
Public 3/4 (still no trailing space!)

Meanwhile, buried in the graveyard:

'''cleaned_s = s.strip().lower()
is_hello = cleaned_s.startswith("hello") and ...
is_hi = cleaned_s.startswith("hi") and ...
return is_hello or is_hi'''

The fix exists. It's just not allowed to run. I call this the triple-quoted graveyard: the correct solution was buried alive while the wrong one inherited the execution runtime.

Same pattern — examples memorized, rule ignored.

Now let's see a place where you can watch the entire algorithm collapse to a single sentence about fruit.

Question 3: Shuffle a Three-Word Sentence

Solving the Examples, Not the Problem

shuffle_sentence('apple banana orange', (0, 2, 1)) → 'apple orange banana'
shuffle_sentence('cat dog mouse', (2, 1, 0)) → 'mouse dog cat'
Words have indices 0, 1, 2 · order is a permutation tuple · 3 public, 3 private tests
This is the purest overfitting exhibit. The two funny cases here are among the best in the entire dataset.

Student 1 — The Baseline

words = sentence.split()
return ' '.join(words[i] for i in order)
Public 3/3 ✓ Private 3/3 ✓ 1 second

The student treated order as data. One line. Full pass. The intended abstraction, visible in working memory.

Student 2 — Learning One Sentence

if order == (0, 2, 1):
    return 'apple orange banana'
Public 1/3 t = 0s

One test case. One hardcoded answer.

Student 2 — Learning Two Sentences

if order == (0, 2, 1):
    return 'apple orange banana'
elif order == (2, 1, 0):
    return 'mouse dog cat'
Public 2/3 t = 69s

Added another case. Progress!

Student 2 — All Public Tests Pass! 🎉

if order == (0, 2, 1):
    return 'apple orange banana'
elif order == (2, 1, 0):
    return 'mouse dog cat'
elif order == (1, 0, 2):
    return 'yellow red green'
Public 3/3 ✓ Private 0/3 ✗ t = 126s

This function is convinced that all sentence shuffling in Python is secretly about one fruit salad.
Overfitting in its purest, most innocent form.

The student didn't learn the transformation rule. They learned the example. Connect back to 10D: the visible tests are not the task.

Student 3 — Listing the Universe

s = sentence.split(" ")
n0, n1, n2 = s[0], s[1], s[2]
if order == (0,1,2): return n0+" "+n1+" "+n2
elif order == (0,2,1): return n0+" "+n2+" "+n1
elif order == (1,0,2): return n1+" "+n0+" "+n2
elif order == (1,2,0): return n1+" "+n2+" "+n0
elif order == (2,0,1): return n2+" "+n0+" "+n1
else:                  return n2+" "+n1+" "+n0
Public 3/3 ✓ Private 3/3 ✓

501 seconds · All 6 permutations listed

Brute force wins a small, perfectly legal victory. The universe of 3-word permutations is exactly 6. This student listed all 6.

The code is correct. The student has just decided that abstraction is optional when the universe is small enough to list. That's not a bug — it's a stage.

Let's move to something more fundamental: what is a pangram, really?

Question 4: Is It a Pangram?

Heuristics vs. Invariants

is_pangram('The quick brown fox jumps over the lazy dog') → True
is_pangram('Hello world') → False
A pangram contains every letter of the alphabet at least once
This question has the most emotionally resonant failure mode. And the funniest.

Student 1 — The Baseline

return set('abcdefghijklmnopqrstuvwxyz').issubset(
    set(text.lower())
)
Public 3/3 ✓ Private 3/3 ✓ Instant

Build the alphabet as a set. Check if it's a subset of the lowercase input. The entire invariant in one expression.

The Pangram Checker That Forgot C

letters = "absdefghijklmnopqrstuvwxyz"
↑ Find the bug.

The function whose entire job is to verify all 26 letters starts by forgetting one. Under cognitive load, even the checking mechanism needs to be checked.

absdefghijk... — the c is silently missing.

Say nothing. Let the audience find it. You'll see the moment it lands in their faces.

Student 2 — Early Attempt

alphabets = string.ascii_lowercase
text1 = text.lower()
for i in text1:
    if i not in alphabets:
        return False
    return True        # ← inside loop!
Public 2/3 t = 0s

Wrong — return True is inside the loop. Returns after the first character.

107 total events · 1 hour 51 minutes of session time

Student 2 — Finding a Shortcut

alphabets = string.ascii_lowercase
text1 = text.lower().replace(' ', '')

count = 0
for i in range(len(text1)):
    if text1[i] in alphabets:
        count += 1

if count >= 26:
    return True
return False
Public 3/3 ✓ Private 0/3 ✗
t = 5709s (~95 minutes in)

Ask the room: is 'aaaaaaaaaaaaaaaaaaaaaaaaaaaa' great literature?

The student found a feature correlated with the answer. That's good instinct, badly applied. 26 total letters ≠ 26 unique letters.

Correlation vs. Invariant

❌ Heuristic

count += 1
if count >= 26:
    return True

Counts total letters. 'aaa...a' = 26 letters but not a pangram.

✓ Invariant

uniq.add(text1[i])
if len(uniq) >= 26:
    return True

Counts unique letters. Correct.

Private 3/3 ✓

The false summit is the moment you think you've solved it. The actual solution comes later, when you ask: what family of inputs would break this?

Four Mental Models

① The Example Memorizer

if order == (0,2,1): return 'apple orange banana'

Solves the visible world, not the rule.

② The Heuristic Guesser

if count >= 26: return True

Finds a correlated shortcut instead of the invariant.

③ The Contract Misreader

tuple(s, r) · card[0]/card[1] · missing trailing space

Computes the right thing, returns the wrong structure.

④ The Regressor

107 events · ends worse than they started

Overwrites a working partial solution while chasing the hidden test.

These aren't Python bugs. They're epistemological strategies. Each one is rational given what the student knows.

What This Means

For test design

If public examples only show 2-char cards, you've invited the index-parser bug. Anti-hardcoding sentinels just need to exist — they don't need to be aggressive.

For code review

When you see a cascade of explicit cases, ask what abstraction the author hasn't seen yet. The fix is often one concept — not a full rewrite.

For debugging

The triple-quoted graveyard is in every codebase. The count >= 26 is in every PR that passes staging but fails production. We're all these students.

The junior who writes an if/elif for every case isn't lazy. They're listing the universe. Now you have words for it.
