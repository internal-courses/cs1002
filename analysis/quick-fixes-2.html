Picture a student — let's call her Priya — checking her work one last time before submitting the pangram problem. She loops over the alphabet. She finds "the quick brown fox" in her head and confirms: yes, all 26 letters present. Her function returns True. She runs the three sample tests. All three pass.

She submits. Zero points.

What happened? Inside her loop, Priya wrote return True the moment she found the first matching letter — and return False if she didn't. Her logic was correct for a single letter. The problem required checking all 26. She exited the loop after checking exactly one.

Now here is the question that matters for this report: how many other students made exactly the same structural error, on this question, in this exam session? The answer is 243. Same mistake. Different names. Different exam halls. Different days.

And across all 60 questions, once you look for these systematic patterns — the failures that aren't really failures, but feedback gaps — nine fixable categories emerge. Together they account for an estimated one in four non-passing submissions. Not knowledge failures. Not irreversible skill gaps. Gaps between what the public tests showed and what the problem actually required.

"These aren't curriculum failures. They are test-design failures — and test-design failures are fixable."

The distinction matters. A curriculum failure means the student doesn't understand the concept. A test-design failure means the exam's public tests didn't show students the full scope of what was being tested — and students, being resourceful, optimized for what they could see. Fix the test; fix the signal.

Act II · P0-1 P0 Priority

The Mimic Trap: 1,348 Students Who Learned the Answer Sheet

The task: write a function divide_into_almost_equal_parts(n, k) that splits the integer n into k parts where the values differ by at most one. The sample tests showed exactly three inputs: (5,3), (16,3), and (12,4).

One hundred and six students in this question cluster alone returned the sample outputs directly. Not variations on the theme — the literal list [4,3,3], [5,5,6], or branching logic like if n==10 and k==3: return [4,3,3]. Their code passes every public test because every public test is a test they memorized.

In the pangram problem, 77 students hardcoded sample pangram strings and checked for them by equality. Here's one — a function that passes three tests by checking for exactly those three strings. The private test uses a different pangram entirely. Score: zero.

The Scale of the Mimic Across all 60 clusters, hardcoding or sample-overfit patterns affect 1,348 non-full submissions — 8.2% of all failures. It surfaces in at least 23 of the 60 questions analyzed. This isn't a quirk of one question. It's a systematic response to a systematic signal: "here are three examples — learn these."

The Fix: One Sentinel Test

The fix requires adding exactly one test that breaks any memorization strategy — a test whose inputs are structurally different from the samples, not harder conceptually. In the algebra expression expander (C085), which uses variable names like a, b, x, y in all sample inputs, the sentinel is:

Revised Public Test — C085 View before/after comparison →

The new test uses multi-syllable variable names (alpha, beta, gamma, delta) that no student could have pre-memorized. A student who truly understands polynomial expansion handles this effortlessly. A student who hardcoded a*c + a*d + b*c + b*d gets zero.

The principle generalizes. For the pangram problem: add a test with a pangram that doesn't appear in the sample. For the division problem: add a test with a value of k not in {3, 4}. The concept being tested doesn't change. The loophole closes.

Act III · P0-3 P0 Priority

The Early Returner: 746 Students Who Quit One Step Too Soon

Here is the bug, stated plainly. A loop iterates over a collection. At some point inside the loop body, there is a return statement. The programmer intended the return to fire after the loop finishes — but they placed it inside the loop, so the function exits after the first iteration.

This bug has a deceptively clean surface. The code runs. It often produces the right answer for simple cases. For the pangram problem, a function that returns after checking the first character will correctly evaluate "The quick brown fox jumps over the lazy dog" because its first non-space character is present in the alphabet.

"243 students made this exact structural error on the pangram question alone. Not a similar error — the same one, reproduced across two cohorts."

The pangram quitter is the canonical case. The four-digit decreasing number problem (C082) adds 82 more — students who check if the first digit is greater than the second and return immediately, never comparing the second to the third or the third to the fourth.

Control-Flow Trap — C082 See example → This student's logic is locally correct: if the first digit is bigger than the second, that's one necessary condition. But it's not sufficient. The function must complete all three consecutive comparisons before deciding anything. For 9413 (which fails because 1 < 3), the function incorrectly returns True because it only checked 9 > 4.

Two-Part Fix: One Test, One Line

The trap test for C012 (arithmetic progression check) looks like this: is_arithmetic_progression([2, 4, 6, 8, 11]) should return False. The error is in the last element — 11 breaks the pattern. Any early returner finds the first gap is 2, returns True, and misses the trap. One test catches it.

The prompt addition is a single sentence: "Important: complete the full scan first; return only after all required elements are processed." It costs nothing. It changes the framing. Students who read it carefully know the expected structure before they start writing.

Act IV · P0-2 P0 Priority

The Parser Edge: 444 Students Who Built a Ruler for Six-Inch Objects

Every sample test in a question is implicitly a specification — it tells students the size, shape, and character of the inputs they need to handle. When all sample inputs share an accidental property — say, all single-digit numbers, or all two-letter column names — students learn to handle exactly that property and nothing more.

The equation solver (C099) asks students to parse expressions like "2x + 3 = 11". Every public sample uses single-digit coefficients, a plus sign, and a specific spacing format. 65 students wrote parsers that break on double-digit coefficients. 30 students wrote parsers that can't handle negative coefficients (minus signs never appeared in the samples). Another 26 are thrown off by slight spacing variations.

The Parser Trap — C099 Public tests only showed "2x + 3 = 11", "5x - 2 = 13", and "-3x + 10 = 1". Students optimized for that shape. A test like "10x + 20 = 60" — double-digit coefficient, same concept — caught 65 students with broken parsers. They had no idea the parser was wrong until the private tests ran.

The Excel column converter (C095) asks students to convert column names like A, B, XFD to numbers. All public examples used one or two characters. 24 students wrote parsers that break on three or four-letter columns.

The Fix — C099 and C095 View before/after test cases →

Add is_equal(solve_for_x("10x + 20 = 60"), 4.0) and is_equal(excel_index("XFD"), 16384) to the public test suite. No change to the question's concept. The parser edge becomes visible before submission.
Act V · P0-4 + P1-2 P0 P1

The Hidden Contract: 430 Students Who Did Everything Right, for the Wrong Problem

Two related failure modes share a common cause: the exam specifies something in the invisible machinery of evaluation that it doesn't adequately explain to students.

File I/O: The Invisible Plumbing

The vowel-uppercase problem (C106) reads input from a file provided to the function as a variable called filename. The hidden grading harness writes stdin content to a temporary file and passes the file path. Straightforward — once you know it. But 27 students called input() inside their function instead, because every Python problem they'd ever seen read data that way. Another 31 parsed k (the "every k-th vowel" parameter) from the first character of the filename itself.

These students weren't confused about the concept. They were confused about the contract — where the data comes from and how to access it. The existing prompt said "read from the file" but gave no starter code showing how. Adding three lines to the template resolves this entirely.

Formatting: When Right Is Wrong

Three hundred submissions have the correct algorithm and the wrong surface. In the sales analysis question (C096), 45 students computed the correct average but didn't round to two decimal places. The engagement rate question (C097) has 103 students with correct rates but no rounding. The number description function (C092) has 122 students who wrote "normal" (lowercase) where the problem required "Normal" (capitalized).

The Philosophical Question Is casing a meaningful concept being tested, or an incidental surface choice? If formatting is not the skill being assessed, the comparator should accept both — or an explicit public test should demonstrate exactly what format is expected. The current setup fails students for the wrong reason.
Act VI · P1-3 + P1-4 P1 Priority

The Scaffold Gap: 956 Students Who Got Lost in the Multi-Function Maze

The chess game analysis question (C110) asks students to implement six helper functions: parse_moves, get_n_moves, get_piece, get_start, get_end, and a final integrator. The public tests only test the final integrator. If any one of the six helpers is wrong, the final result is wrong — but there is no feedback indicating which helper failed.

221 students in this cluster left the skeleton in a partially-implemented state — some helpers done, others not. A student who completes parse_moves correctly but gets get_piece wrong sees the same undifferentiated "Wrong Answer" as a student who implemented nothing. Neither learns where to look.

"816 non-full submissions across multi-function tasks. Every single one would benefit from knowing which helper broke first."

The fix has two parts: first, replace ... stubs with raise NotImplementedError("Implement parse_moves") so students get immediate feedback if they forget to implement a helper. Second, add one small smoke test per helper — not a complete integration test, just a minimal sanity check that the helper works at all. Students can then debug incrementally.

The dispatch-branch coverage fix (P1-4) addresses the same structural issue for task-driven functions. In C096's analyse_sales_data, which accepts a task string like "total_revenue" or "top_selling_product", 140 students implemented only one or two of the four required branches. One minimal public test per branch would reveal the gap instantly.

Act VII · P2 P2 Priority

The Silent Catastrophe: When Two Variants Become Two Different Exams

The P2 finding is different in kind from everything above. It doesn't affect hundreds of students — it affects entire cohorts without anyone realizing it.

In the file-content zig-zag shift problem (C020), the analysis found that one variant of the question was effectively a different task than its counterpart. Students in one sitting were solving a zig-zag shift; students in the parallel sitting were solving what amounted to a different file-processing task. 89 of 136 submissions in one variant (65.4%) solved the wrong task — and the exam graded them on the wrong rubric.

Variant Drift — The Release Risk See the equivalence comparison →

When two variants of what appears to be the same question actually test different things, the consequences are not just wrong scores — they are incomparable scores. Students from one sitting cannot be compared to students from the other. The fix is not a test change; it's a pre-release validation script that fails the release if variants diverge beyond metadata fields.

This is the one fix that requires a process change rather than a content change. But it's also the one fix that, if absent, renders all comparison statistics unreliable at cohort scale.

What This Is Not

This analysis does not claim that 4,000 students are definitively recoverable — only that their failure patterns match fixable test-design gaps. Some of those students would have failed the revised exam too. The numbers are upper bounds.

What the analysis does establish is that these failures are systematic, not random. When 243 students across two exam cohorts make the same structural error, that error is a signal about the exam as much as about the students. When 1,348 submissions show hardcoding patterns, those students were doing what the test feedback trained them to do.

The nine fixes don't make the exam easier. They make it more honest — aligning what the public tests show with what the private tests require. Students who understand the concept will pass the revised exam just as easily. Students who were gaming the visible tests will be caught earlier, in time to actually learn the concept, rather than after they've submitted and scored zero.

That's the goal. Not a different exam. A better-calibrated one.
